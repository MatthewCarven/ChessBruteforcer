Method. As results-2026-10-20-split.txt: bench's six positions at depth 9, a fresh 16 MB table each search, the bot's
tables object over an empty folder; a recording run, a check run, then 6 rounds (+1 dropped) of arms, rotated, every
arm run twice at depth 6 first so the JIT compiles tier 1 from all of them. Removal arms replay one piece's answers on
the identical tree (checked every run: the same nodes, every replayed stream read exactly to its end). New since the
morning: generation removed by kind (Negamax's lists, quiescence's captures, its evasions), castling's attack tests
removed, and the prototype's arms:
  sets         a set per colour and piece type kept in Position.Put (12 + 2 bitboards), nothing reading them
  tables       and IsAttacked from them by table (InCheck, castling's tests): knights, kings and pawns a set per
               square, rooks and bishops by PEXT into a table per square (64-bit entries, ~840 KB); the tablebase's
               piece count by popcount. Today's answers, so the identical tree.
  tables16     the same with 16-bit entries expanded by PDEP (~210 KB): the L2 question
  bbo          and generation from the sets in today's order (from-square up, per piece as MoveGenerator has it):
               today's lists move for move, so the identical tree
  bb           generation from the sets in the lab's order (pawns set-wise, then knights ... king, castling): the
               same moves in another order, so PickNext breaks ties another way: its own tree
  full...      the same with the network on; vbb / vbbo check the sets' lists against today's at every generation

What the prototype says:
- Attack tables beside today's board are worth +16% (+14.6% at 256 MB), the identical tree. An attack test by table
  costs ~8 ns in place against 36-47 by walking rays (the 54 ns a node is InCheck's and castling's tests, ~60, and the
  tablebase's count, ~4, less the sets' upkeep, 9). More than the lab's -68%: in the search the tables stay warm.
- The L2 question has an answer: 840 KB of tables beside the network's 1.5 MB cost nothing measurable at one thread,
  at 16 MB or 256 MB of table (64-bit and 16-bit entries within 1-2 ns of each other, either way round). The bot's 8
  threads each have their own core's 1.25 MB L2, so the same should hold there; 16-bit entries are the fallback.
- Generation from the sets is worth 26 ns a node in today's order and 52-53 in the lab's: keeping today's order (a type
  switch per piece, pawns one at a time, sliders ray by ray) gives back half the gain. The lab's order changes which
  quiet moves come first among equal scores, and LMR reduces by place in the list, so the tree changes: -9.0% nodes
  at bench 9 (-10.7% at 256 MB). Smaller is not better or worse by itself: a match would say.
- The prototype's upkeep is the plain one (both arrays updated in every Put, 9 ns a node); one XOR of the from and to
  squares per set in MakeMove should be about half that: a little more than measured, not counted below.
